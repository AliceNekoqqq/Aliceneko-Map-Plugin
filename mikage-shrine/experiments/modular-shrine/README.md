# 神社模块建设接轨小样

当前状态：独立、只读画面小样，未替换 1.47.0 角色卡。复用发布版 1.30.1 MVU 的真实初始状态和 1.47 生活陈设素材。不是新的建设经济，也没有施工过程美术。

## 与现有建设的对应

| 原字段 | 1～3 的画面 | 4（已完工）的画面 |
| --- | --- | --- |
| 神社.鸟居 | 基础鸟居 | 完整注连绳、金饰鸟居 + 手水钵 |
| 神社.参道 | 土径 | 石参道 + 两座石灯笼 |
| 神社.社务所 | 基础社务所 | 接待侧屋 + 绘马架 |
| 神社.拜殿 | 基础拜殿 | 完整屋顶、朱栏与奉纳箱 |
| 神社.庭院 | 基础樱树 | 水池 + 花丛 + 第二株樱树 |

0 是原字段允许的“尚未修复”，小样隐藏对应设施；空场拼装仅用于验证部件可以分别添加。旧初始状态均为 1，因此正常读档不会把现有建筑清空。缺失设施字段按初始值 1 显示，非法进度拒绝读取。1～4 始终保留原有修缮语义，不被当成四个新升级等级。

每个建筑/附属物有稳定 id、所属设施和世界坐标。完工只替换该设施模块或增加其附属物，其他模块不变。地面没有预画建筑，所以不存在新增层叠在旧建筑上的重影。相机固定，部件不跟着升级移动。

生活陈设直接读取 `生活.布置`，保留 decoration id、item、zone、slot 和 lit；只把原槽位映射为新世界坐标。六件已有实绘陈设复用 1.47 图集；其他已知槽位中的无专属美术物件暂显示通用小物块。未知槽位不绘制，不修改存档。小样不提供库存、收起、点灯或正式建设写入。

## 运行与检查

```bash
python experiments/modular-shrine/build.py --output /absolute/path/preview.html
node experiments/modular-shrine/test.mjs
CHROMIUM_PATH=/path/to/chromium node experiments/modular-shrine/browser-test.cjs /absolute/path/preview.html
```

单文件 HTML 内含素材和中文字体，可离线打开；按钮只操作内存副本。支持原状态对象、`stat_data` 和 `data.stat_data` 三种 JSON 包装。生成器默认输出同目录 preview.html；交付文件通过 --output 指定。测试直接提取现役 MVU 的 ShrineInitial，不另造一份初始存档。

## 正式卡接入时必须处理

1. 从 1.47 manifest 指向的 scene 1.43 解码 StatusbarHTML，局部接入 R01 scene 图层；外围状态栏/六入口/四工具按钮继续复用。不能用较早 src/statusbar.html 覆盖发布模块。
2. 现有 render(snapshot) 把同一快照传给 project/render。任务、规划、开工、施工、扣料、章节结案保持原领域处理，显示层不发建设事件。
3. 仅 R01 使用模块底图；R02～R10 保留原背景。阻止 R01 updateLight 的旧背景异步加载覆盖新底图；时间预览只改显示参数，不能回写环境时间。
4. 重画 R01 行走网格、碰撞和角色/热点锚点。新场景的建筑位置不同，不能继续沿用旧画的导航坐标。保留人物衣装、行走帧与交互行为。
5. 原生活陈设层和新画布只能有一个负责 R01 陈设，避免重复显示；保持原物件点击行为。关闭/切地区/重载时清理订阅。
6. 做宿主内旧存档、逐章完工、聊天切换与移动端验收后，才打包新的轻量角色卡。当前小样没有完成这些正式接入步骤。

## 对玩法的判断

现有系统能支持“五项修缮逐项带来永久画面变化”，不够支撑持续扩建。修好五项以后，原状态不再增长；只接上画面仍会到顶。真正的乐高式扩展应在下一阶段新增独立扩建记录（模块 id、地块、升级级别、前置与花费），并经正式领域校验，不复用/篡改现有 1～4。

建议先补可选地块和明确可见回报：庭院选池塘/花圃、社务所选茶席/绘马廊，每条线允许继续升级；旧五项完工是扩建前置。玩家可以选择发展方向，建设才会从固定章节清单变成有取舍的经营。当前小样是固定锚点的组合验证，尚不是自由拖放、无限扩建或完整新玩法。
